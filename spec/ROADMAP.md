# Roadmap

## Vision
Kafka3O is a multi-cluster Kafka console for developers and operators: one web UI (Kafka3O-UI) shows every cluster side by side — health, topics, messages, consumer lag. Each cluster is fronted by its own small, stateless gateway (Kafka3O-Gateway) that owns the broker connection and credentials close to that cluster; the browser never talks to Kafka directly.

The console should be comfortable for dense technical data, easy to navigate, and explicit about connection problems and write outcomes. M6–M8 turn the existing functional pages into a consistent, accessible operator interface without changing the gateway API or the completed M1–M5 behavior. M9 extends the gateway and UI with explicitly confirmed Kafka configuration and partition administration. M10 adds local/Cognito login, global and per-cluster authorization, Production safeguards, and an attributable audit trail. M11 simplifies signed-in navigation and lets each user tailor the console's appearance for comfort and readability, without weakening the accessibility baseline. M12 lets operators fix stuck consumers and operate Kafka Connect from the console, under the same roles, Production rules and audit as every other write. M13 adds topic backups to S3-compatible storage through Kafka Connect, with restores into the original topic. M14 turns consumer groups into a list with one page per group, and M15 adds a per-cluster Metrics tab with what Kafka itself reports, exportable as a download and for Prometheus. M16 moves backup setup and restores onto the topic page, with a few backup settings and restores limited to a time range or chosen partitions. M17 adds the metrics most worth alerting on: consumer lag per group, controller quorum and leader balance, and Kafka Connect and backup health. M18–M22 add `kafka3o`, a command-line client (Kafka3O-cli) that gives the UI's information and actions in a terminal across every cluster the user may access, as tables for people and JSON for scripts.

## Out of Scope
- A gateway serving more than one cluster
- The UI connecting to Kafka directly
- Cluster-wide broker default changes, ksqlDB administration, and Redpanda-specific management APIs
- Kafka ACLs/quotas, Kafka Connect, and Schema Registry administration in M10; these are deferred backlog candidates, not part of the authentication release
- Replaying, copying, or transforming messages between topics, except restoring a topic's own backup into that topic (F50)
- Free-form connector configuration from the UI; backup connectors use configurations generated by the Gateway from a fixed set of choices (F54), and generic create/update/delete stays F48
- Persistence in the gateway (no database; stateless)
- Invented metrics or Gateway-to-Kafka connection-setting changes from the UI
- CPU and memory metrics, and any metrics source other than Kafka itself (user decision 2026-11-10: Kafka StatefulSets stay unchanged and no metrics-server is installed)
- Direct SSO integrations other than Amazon Cognito in M10; additional providers are in the backlog
- Creating, updating or deleting Kafka Connect connectors in M12 (backlog F48), and showing connector configuration values that may hold secrets
- Adding, removing or retargeting registered clusters from the UI; the cluster registry changes only through a repository change (dropped F17)
- The CLI talking to Gateways directly (it always goes through the Console), an interactive full-screen terminal UI, and Cognito sign-in from the CLI (backlog F69)
- Appearance preferences synced to a Console account, ADMIN-enforced appearance defaults, free-form color pickers or custom CSS, and fonts loaded from external sites

## Features
- **F1** User can see every configured cluster on one page with its health (gateway reachable, cluster reachable, broker count)
- **F2** User can open a cluster and see its brokers and controller
- **F3** User can list a cluster's topics with partition count, replication factor and approximate message count, and filter them
- **F4** User can open a topic and see its partitions (leader, replicas, ISR, start/end offsets) and its config
- **F5** User can read a topic's latest messages (key, value, headers, timestamp; value as text, JSON or base64)
- **F6** User can start reading from a chosen partition, offset or timestamp
- **F7** User can search a topic for messages whose key or value contains some text, within a bounded scan
- **F8** User can find a topic by name across all clusters at once
- **F9** User can copy a link that opens directly to one message
- **F10** User can see consumer groups with state, members and lag per partition
- **F11** User can see which consumer groups read a given topic and how far behind they are
- **F12** User can only reach a gateway when authenticated
- **F13** User can produce a test message (key, value, headers) to a topic
- **F14** User can create or delete a topic
- **F18** User can navigate every page through a consistent application shell, active cluster, breadcrumbs and contextual tabs
- **F19** User can read and operate every existing page with consistent styling, accessible controls, responsive layouts and clear states
- **F20** User can manage per-gateway connections in a dedicated panel instead of permanent header forms
- **F21** User can explore clusters, brokers, topics and configuration through organized overview and detail pages
- **F22** User can read and search messages in a compact list with a selected-record inspector for payload, headers and exact position
- **F23** User can inspect consumer groups and partition lag through summary-to-detail navigation
- **F24** User can produce messages and create or delete topics through contextual forms with explicit pending, confirmed and uncertain outcomes
- **F25** User can inspect and change editable per-broker and topic Kafka configuration while sensitive and restart-required settings remain protected
- **F26** User can increase a topic's partitions and request manual replica placement while inspecting reassignment progress
- **F27** User can sign in with a local account or Amazon Cognito SSO and end or recover their Console session safely
- **F28** An authorized administrator can manage users, Cognito group mappings, and global/per-cluster role assignments
- **F29** User can access only permitted cluster resources and actions, with authorization enforced by the Gateway as well as the Console
- **F30** An authorized administrator can flag a cluster as Production, where only an ADMIN for that cluster can perform Kafka mutations
- **F31** An authorized user can inspect an attributable audit trail of authentication, access-control changes, denied actions, and Kafka mutation outcomes
- **F45** User can choose the console's color mode, color theme, font, text size and density, remembered in their browser
- **F15** User can reset an inactive consumer group's offsets to earliest, latest or a timestamp, with a preview
- **F35** User can inspect a cluster's Kafka Connect connectors and tasks and pause, resume or restart them
- **F47** User of the secured console sees no Gateway credentials control, because every cluster is reached through the Console
- **F49** User can start, list, stop and delete continuous backups of a topic's messages to S3-compatible storage
- **F50** User can restore a topic's backup into that topic after confirming that restored messages are appended
- **F46** User can work signed in with a compact session indicator, a separate administration page shown only to administrators, and clusters that open on their topics
- **F52** User can scan a cluster's consumer groups in a list and open one group's page with its offsets per topic and partition
- **F41** User can see a cluster's broker disk use, partition health, topic sizes and throughput on a Metrics tab, as reported by Kafka
- **F53** User can export a cluster's metrics as a CSV/JSON download and through a Prometheus endpoint on the Gateway
- **F54** User can set up and manage a topic's backup on its Backup tab, choosing its start point, compression, file size and flush time
- **F55** User can restore a topic's backup from its Backup tab: everything, a time range, or chosen partitions
- **F56** User can go from the cluster's Backups overview to a topic's Backup tab
- **F57** User can see each consumer group's state and lag on the Metrics tab and in its exports
- **F58** User can see the controller quorum's health and how partition leaders are spread over brokers on the Metrics tab and in its exports
- **F59** User can see Kafka Connect connector and task states and each backup's health on the Metrics tab and in its exports
- **F60** User can sign in to the Console from the terminal with a local account, stay signed in between commands, and sign out
- **F61** User can list every cluster they may access with its health from the terminal
- **F62** User can list and filter topics across all clusters and inspect one topic (partitions, configuration, consumers, backup) from the terminal
- **F63** User can inspect a cluster's brokers, broker configuration and metrics from the terminal, and export the metrics as JSON or CSV
- **F64** User can read a topic's messages (latest, from an offset or a timestamp) and search them from the terminal
- **F65** User can list consumer groups and see one group's offsets per topic and partition from the terminal
- **F66** User can make the UI's Kafka changes from the terminal (produce, create or delete a topic, change configuration and partitions, reset offsets) with confirmation and Production reasons
- **F67** User can operate Kafka Connect connectors and topic backups and restores from the terminal
- **F68** An administrator can query and export the audit trail and manage accounts, roles and cluster environments from the terminal

### M10 — Authenticated, authorized and auditable cluster operations
- **Status:** Done (2026-11-08) — the EKS-D manual-test deployment now runs the secured stack; shared-token access is removed. Real Cognito remains unverified until a User Pool exists.
- **Features:** F27, F28, F29, F30, F31
- **Goal:** Give each operator an identity and explicit access, enforce Production protection at the Gateway, and record who attempted or performed each sensitive operation.
- **Approved direction (2026-11-06):**
  - Local username/password login and Amazon Cognito User Pool SSO first. Other direct identity-provider integrations remain in F42.
  - Add one central Console backend for login, secure server-side sessions, access management, cluster classification and audit persistence. Keep one stateless Gateway per Kafka cluster; the backend does not move Kafka credentials into the browser.
  - Use a dedicated durable SQLite volume and one Console instance. A separate test-only database/volume may be created on `eksd-01`; Kafka volumes are not reused.
  - Support both global and per-cluster `VIEWER`, `OPERATOR`, and `ADMIN` grants. Global grants apply to all registered clusters; cluster grants add access only to their cluster. No grant means no access; grants combine by highest role, with no implicit deny/override model in this release.

  - The extra ADMIN-only mutation guard applies **only to Production**. Non-Production writes still require the normal action permission; this does not make every authenticated user a writer.
  - Production covers every Kafka mutation: produce, topic creation/deletion, broker/topic configuration changes, partition increases and replica reassignment. ADMIN operations still require the existing validation/confirmation plus a recorded Production change reason.
  - Gateways authorize the actual request against current server-owned policy, including direct API calls. Shared-token access and the automatic manual-test proxy must not bypass M10 policy.
  - Persist authentication/security events, policy changes, denials, mutation intent and the accepted/rejected/unknown outcome. Provide a permission-scoped audit page with filters and export; exclude credentials, payloads and sensitive configuration values.
