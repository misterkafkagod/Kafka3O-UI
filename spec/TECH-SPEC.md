# Technical Spec

Covers both repositories: **Kafka3O-Gateway** (one per Kafka cluster) and **Kafka3O-UI** (one UI talking to all gateways). The implemented M1–M9 baseline calls each gateway directly over HTTPS with CORS (or through the explicitly enabled local manual-test proxy). The planned M10 architecture instead uses a central Console backend for identity, sessions, policy and audit; its trust flow is specified below and is not deployed.

## Policies
- Project type: Open source (Apache-2.0) · CVE policy: zero unpatched critical/high in shipped dependencies

## Conventions
- SOLID: all five principles; dependencies injected as abstractions (Go: constructor arguments; TS: function parameters)
- One method per file: one class (or function) with one method, no private helpers (helpers are their own files, injected)
- Naming (Go): file named after the action — `list_topics.go` → interface `ListTopics` with `Execute(ctx)`, unexported struct `listTopics`, constructor `NewListTopics(deps)`
- Naming (TS): `listTopics.ts` → exported function type `ListTopics` and `export function listTopics(gateway, clusterId)`; components and hooks likewise (`TopicTable.tsx` → `TopicTable`, `useTopics.ts` → `useTopics`)
- Injection scope: I/O and side-effecting actions are always injected; pure functions without I/O and child components may be imported directly
- Inline functions: named logic (transforms, comparators, predicates, mappers) lives in its own file with its own test. Only logic-free framework glue may be inline: an HTTP handler closure that just calls an injected action, a JSX `.map` render callback, composition-root wiring
- Exempt: data-only types (DTOs, records, enums, TS types); test files (`list_topics_test.go`, `listTopics.test.ts`; many tests each); the composition root and test helpers need no own test file (covered by build and demo)
- Patterns: Ports and adapters (light) — actions depend on Kafka interfaces, franz-go lives only in `internal/kafka`; solves unit testing without a broker
- Patterns: Composition root — wiring only in `cmd/gateway/main.go` and `src/main.tsx` for the current processes; the planned M10 Console process gets its own composition root. This assembles mandatory DI once per process
- Rules (Gateway): HTTP handlers never see franz-go types; adapters map to DTOs
- Rules (Gateway): every Kafka call uses the request `ctx` with the configured timeout (default 3 s), which must stay below the UI's gateway timeout (5 s)
- Rules (Gateway): errors are problem JSON with a stable `code` (`cluster_unreachable`, `not_found`, …), built as `httpapi.Problem` (embeds `huma.ErrorModel`, adds `code`)
- Rules (Gateway): no durable application state survives a Gateway restart; M10 identity/policy/audit state belongs to the central Console store, not to the per-cluster Gateway
- Rules (UI): components never call `fetch`; all I/O goes through the injected `FetchJson` (`src/gateway/fetchJson.ts`)
- Rules (UI): gateway query keys start with `["gateway", gatewayId]`
- Rules (UI): M1–M9 use runtime `/config.json`, never build-time cluster env. M10 secured mode returns the authorized runtime cluster registry/capabilities from the Console backend; client config is not an authorization or Production-classification source
- Rules (UI): the static host serves `index.html` for client routes (`/clusters/*`); Vite dev already does
- Rules (M5 baseline): tokens are stored in browser session storage for the configured HTTPS gateway only, never in URLs or runtime config; the UI must run in a secure context, authenticated redirects are rejected, and credential changes clear gateway query caches. M10 secured mode replaces this with an opaque HttpOnly Console session and clears caches on identity/access changes; legacy tokens are not accepted as a parallel authorization bypass

## M10 identity, authorization and audit (planned)
Scope: F27–F31 in [FUNC-SPEC.md](./FUNC-SPEC.md#f27--local-and-cognito-sign-in-planned-m10). These are target contracts, not claims about current code, dependency scans or deployment. The user approved the central backend, Cognito-first SSO, local login, global plus per-cluster roles, and a Production-only extra mutation guard.

### Components and persistence
- Retain the React static build and one Go Gateway per Kafka cluster. Add one Go Console backend alongside the Gateway codebase, with its own composition root/process; it serves/proxies the UI's same-origin authenticated APIs. Reuse existing HTTP, DI and problem-error patterns rather than adopting a new frontend/server framework.
- The Console owns a dedicated SQLite database for local password hashes, identity links, server-side sessions, role/group mappings, the registered cluster environment/policy, short-lived delegations and append-only audit events. Gateways remain stateless. Run exactly one Console instance on a dedicated persistent volume with a local filesystem supporting SQLite locking; this choice is not an HA deployment. The driver version and initial migration are selected; deployment-specific retention and SQLite-consistent backup/restore remain to be verified. No in-memory-only substitute qualifies for M10 completion.
- The storage foundation uses WAL, `synchronous=FULL`, foreign keys, a bounded single-connection pool, versioned migrations and owner-only database-file permissions on Linux. An adjacent lock file enforces one Console process per canonical database path; its permissions must be owner-only on Unix and configured with restrictive ACLs on Windows. The empty file remains after shutdown and must not be deleted or replaced while in use. Protect the directory and prohibit hard-link aliases. SQLite online snapshots use `VACUUM INTO` a new owner-only file; backup and restore, access restrictions, retention and disk-full behavior must also be verified for the deployed volume. Never copy a live database file without accounting for its WAL. SQLite documents [WAL filesystem limitations](https://sqlite.org/wal.html) and [online backups](https://www.sqlite.org/backup.html).
- Registration binds a stable logical cluster/Gateway ID to an allowlisted verified-TLS endpoint and its expected Kafka cluster identity. Bind policy to that server-owned ID, not a display name or client-supplied URL. Replacing/retargeting a registration is a separately authorized, audited administrative action; do not silently reuse a non-Production policy for a different Kafka cluster.
- Use least-privilege deployment-managed Kafka service accounts at each Gateway. Cognito users are Console identities, not automatically Kafka users. Kafka sees the configured Gateway principal; M10 application audit supplies the actor attribution. Optional end-user Kafka impersonation is F43 and requires separate broker support/discovery.

### Local and Cognito authentication
- Local users are administrator-provisioned; use a maintained adaptive password-hashing implementation, constant-time verification, bounded password lengths, login/reset throttling and generic authentication failures. Bootstrap the first local global ADMIN out of band with a single-use secret; never ship a default password or persist plaintext credentials.
- The standalone local-authentication foundation uses Argon2id and records a durable 15-minute sliding window of all login attempts: at most 10 per normalized username, 60 per client address, and 300 globally. Bootstrap has a separate durable global limit of 10 attempts per 15 minutes; rejected attempts are anonymously audited without credentials or submitted usernames. Client addresses must come from the direct peer or an explicitly trusted proxy. Bootstrap/password changes and their success audit records are atomic, but the code is not yet a deployed authentication boundary: restricted deployment access, end-to-end password-change gating, session revocation and recovery remain required before exposure.
- The offline `cmd/console bootstrap` command is restricted to the database-owning operating-system account and refuses terminal or regular-file input. The expected one-use secret is supplied through an environment variable; a trusted local process pipes the presented secret, username and temporary password. Credentials must not enter shell history, arguments, logs or plaintext files. This command is not deployed and is not an administrator-recovery mechanism.
- The local-account creation service requires a current local global ADMIN session, binds a single-use reservation to that session and the new account ID, and rechecks authorization after hashing. Creation and its audit outcome commit atomically; the account starts enabled with no role grants and must replace its temporary password. Duplicate normalized usernames, stale/replayed reservations and audit failures fail closed. Four concurrent hashes are admitted per service. The loopback HTTPS creation API derives its actor from the authenticated session, requires exact Origin and session-bound CSRF, and rejects role/actor/session input. Unknown or lost-response outcomes require investigation by operation ID when available rather than automatic retry; there is not yet a creation UI.
- The loopback HTTPS `GET /api/admin/local-accounts` route lists only local accounts for a current local global ADMIN, rechecking the session and grant transactionally. It returns an operation ID and a username-ordered, non-snapshot page of IDs, usernames, enabled states and mandatory-password-change flags; it never returns hashes, credential versions or grants. `limit` defaults to 50 and is capped at 100; `after` is the preceding account ID and an empty `nextCursor` ends pagination. Responses are `no-store`. Successful listings, authorization denials and service-level invalid cursors are audited without usernames or submitted cursors; malformed query parameters are rejected before the listing operation. Audit insert or commit failure returns no account data. This foundation is not a complete access-management UI or grant API.
- Cognito uses an Amazon Cognito **User Pool** OIDC app client and managed login, not an Identity Pool or an AWS EKS integration. Use authorization code + PKCE S256, state and nonce; exchange codes server-side and keep any client secret/provider tokens out of browser storage. Callback and logout destinations are exact allowlisted URLs.
- P53's [fixture discovery](./discovery/cognito-user-pool-fixture.md) is documentation-derived, not a live pool test. Configure the exact issuer separately from the managed-login domain; verify discovery issuer and expected HTTPS authorization/token/JWKS endpoints, disable redirects, and use explicit client authentication to prevent library auto-retries. Provider outages must not prevent local login. The eventual real pool, native-browser callback/cookies and deployment require separate verification.
- The standalone Cognito verifier now checks exact discovery endpoints over verified HTTPS, RS256 signatures and rotation, exact issuer/client, strict expiry, nonce, token use and authorized party. Provider documents are capped at 4 MiB and ID tokens at 1 MiB; only verified opaque subjects and group names are returned, with no automatic grants. Its synthetic TLS fixture covers invalid metadata, certificates, signatures, claims, outages and key rotation. Cached keys can verify unexpired tokens during a provider outage; required session refresh must independently fail closed. No Cognito routes or real User Pool have been tested.
- The standalone authorization-attempt service uses independent CSPRNG values, stores only state/browser/nonce digests and an AES-256-GCM-encrypted PKCE verifier, and binds the ciphertext to those digests, the configured provider and callback. Its externally managed random 32-byte key is not stored in SQLite. At most 1,000 pending attempts live for five minutes from request start. A matching unexpired browser-bound attempt is consumed once with audit in one transaction; queued expiry, replay, malformed input, audit failures, tampering and uncertain commits fail closed. Key, provider or callback changes and the upgrade from the earlier unbound format invalidate pending attempts.
- Separate trusted-marker authorization-attempt actions combine the transient-cookie and stable-marker digests with a domain-separated hash; bound verifier authentication additionally covers the operation ID and expiry. Wrong, missing or unbound markers cannot consume a bound attempt, and the private consumed proof is rejected by the unbound exchanger before provider contact. Bound actions recheck the transaction decision time and deadline before releasing credentials; uncertain post-commit time changes return no credentials. Unbound attempt behavior remains compatible. A bound code exchange and its session proof carry the same private marker digest; both manager and storage reservation/creation checks require the match, and bound and unbound proofs are mutually exclusive. Wrong markers cannot consume the correct proof. Stable-marker lifecycle and browser integration remain unfinished, so no SSO route may use these primitives yet.
- Standalone browser-authorization helpers construct an `openid` code-flow URL with state, nonce and PKCE S256 for the verified provider and exact callback, rejecting altered, foreign, expired or backwards-clock starts. The browser binding goes in a short-lived host-only Secure HttpOnly SameSite=Lax cookie, not in the URL; matching cookie deletion is provided. The PKCE verifier, client secret and provider tokens are not included in the URL. The application session cookie remains Strict. The helpers expose no route and do not yet protect against replacing an existing browser session.
- The standalone browser-callback parser accepts at most 8,192 raw query bytes, one canonical state and exactly one valid authorization code or provider error. Duplicate/unknown parameters, malformed encoding, control characters and oversized values are rejected; provider error descriptions and URIs are discarded, not displayed or followed. The browser-cookie reader rejects missing, duplicate or noncanonical bindings. The exchanger shares the same code validator and rejects invalid codes before provider dispatch. A future handler must consume and audit the matching attempt for both success and provider denial, clear transient cookies and avoid logging the callback or binding; no route is exposed yet.
- The storage foundation can optionally bind a newly created local or Cognito session to the digest of a separate stable browser marker. In one transaction it rejects and audits a competing active session or records the new current binding; replacement is permitted only after revocation, disablement, idle expiry or absolute expiry. A successful replacement also irrevocably revokes the old session, deletes any retained Cognito credential and writes a redacted retirement audit in that same transaction. Bound issuance rechecks a non-regressing clock and session deadlines before and after commit, and Cognito exchange freshness. Only the exact conflict sentinel confirms a durable denial; audit, commit and uncertain outcomes must not be treated as safe retries or ordinary invalid sessions. Trusted-marker manager issuance actions reject missing or mismatched markers before consuming Cognito proofs and return no credentials on conflict or uncertain outcomes. Separate bound session-use and grant storage actions check both the session digest and current marker-to-session binding transactionally, recheck current identity, deadlines and direct/verified-group grants, and deny stale Cognito claims without refreshing. Bound logout lookup and revocation also check the current binding; revocation, provider-credential deletion and audit commit together, including when a current Cognito session is otherwise unavailable. Trusted-marker manager logout actions never refresh and cannot revoke a replacement; the eventual HTTP handler must validate Origin and CSRF. Local administrator actions can accept a marker digest only through a trusted actor and transactionally recheck its current binding, session state and global-ADMIN grant, including after reservations. Separate bound refresh inspection and reservation check the current binding and non-regressing clocks; a durable per-generation reservation blocks replay and session use, and an uncertain or expired post-commit result returns no credential material. A read-only pre-dispatch guard rechecks the exact reservation, binding, credential, snapshot and deadlines but does not contact the provider; completion rechecks the binding after provider dispatch. Bound failure auditing uses the historical session digest and exact reservation, allowing a failed or unknown outcome after replacement or revocation without changing the replacement; unbound auditing rejects existing bound sessions. An old session cannot revive or revoke a replacement. Existing unbound paths remain independent of the binding table and reject bound sessions. The opt-in manager can resolve a session and its grants using a trusted marker digest, but no route supplies it; marker lifecycle and browser integration remain unfinished. A future Cognito identity-disable administration path must atomically revoke sessions and remove credentials even without a replacement.
- Standalone stable-marker helpers generate 32 random bytes, encode them canonically without padding and derive a domain-separated digest from the hash of the raw bytes. The raw Cookie-field reader returns only the digest and rejects missing, malformed and duplicate fields, including malformed duplicates; session validation rejects reuse of a marker value as a session or CSRF token. No cookie setter or route is exposed. First-time initialization, lifetime, delayed responses and real-browser concurrency remain unresolved, so these helpers must not yet enable SSO.
- An exploratory Chromium probe with intercepted synthetic origins observed that a cross-site top-level callback omitted a Strict session cookie while a subsequent same-origin fetch included it; an earlier delayed response also overwrote a newer HttpOnly cookie. This is not a safety proof or an end-to-end provider test. Actual redirects, network interruptions, other browsers and concurrent login/callback flows remain unverified.
- Stable-marker protocol ([discovery](./discovery/browser-marker-protocol.md)): SSO requires `navigator.locks`; without it the UI does not offer SSO and local login is unchanged. Only `POST /api/session/browser` sets `__Host-kafka3o_browser` (Secure, HttpOnly, Path=/, SameSite=Strict, 400-day Max-Age): one valid marker returns 204 without `Set-Cookie`, no marker mints one, and any malformed or duplicate marker field returns 409 without overwriting it. The UI performs ensure, SSO start, callback completion and Cognito logout inside one exclusive `kafka3o-browser-marker` Web Lock and never aborts those requests. The cross-site Cognito callback navigation carries the Lax pre-authentication cookie but not Strict cookies, so the SPA serves `/auth/cognito/callback`, replaces its URL, and completes with a same-origin `POST /api/session/cognito/callback` of the raw query. Real-browser probes (Chromium 156, Firefox 157, Chrome 156, Edge 156) showed one marker under the lock versus overwrites without it, no late application after a closed tab, and no cookie after a dropped connection; a live Cognito User Pool completed exchange, code-replay denial, refresh without rotation or nonce, revoke and logout. Safari, HTTPS WebKit and multi-profile behavior remain unverified.
- P53 composition (2026-11-07): `cmd/console serve` enables Cognito only with a complete `KAFKA3O_CONSOLE_COGNITO_*` set, discovers it in the background and reports `GET /api/session/cognito`; `POST /api/session/browser`, `/api/session/cognito/start` and `/api/session/cognito/callback` follow the stable-marker recipe; marker-carrying requests resolve bound sessions first, local login and SSO refuse to replace a live bound session, and Cognito logout revokes locally before returning the allowlisted provider logout URL. Local-account administration returns 403 for Cognito sessions until group bindings exist. The built preview passed opt-in synthetic-provider and provider-outage integrations and an opt-in live test against a test User Pool (managed login, exchange, bound session, revocation, provider logout redirect, replay denial, log redaction) with every TLS check enabled; the live browser step intercepts Console-origin requests instead of trusting the loopback certificate. Not verified: the SPA landing page and Web Locks in a browser against the real Console, Safari, Cognito group-change propagation, refresh-token rotation, and any deployed or EKS-D environment.
- A standalone bound provider exchange carries the marker digest through reservation, pre-dispatch guard and failure audit, sends at most one request, and returns a private marker-bound completion proof. A wrong, absent or unbound marker cannot consume it; the first correctly bound completion attempt consumes it even when later checks fail. Completion transactionally rechecks the current binding, reservation, identity, encrypted credential, verified snapshot and deadlines before atomically storing the next encrypted generation and redacted audit. Replacement, revocation or disablement during provider dispatch cannot restore the old session. Uncertain requests or completions are never automatically retried. Synthetic tests cover both client modes, rotation and retention, in-flight replacement, clock and state failures, restart and redaction; live Cognito remains unverified.
- The standalone code exchanger durably claims each consumed attempt before sending one verified-HTTPS token request with explicit public-client or confidential Basic authentication. Reservations require the private consumed proof. The bound path rechecks marker, non-regressing transaction time, attempt expiry and verified-claim freshness before returning a privately bound session proof; mismatches do not reserve the valid proof. It refuses redirects, caps token responses at 1 MiB, rechecks queued expiry, verifies the ID token and withholds its in-memory refresh token on audit or uncertain failure. Interrupted or uncertain exchanges are not retried. Synthetic tests cover both client modes and failure paths. The exchanger alone does not expose a browser route; the separate session foundation persists encrypted refresh tokens, while live Cognito remains unverified.
- The standalone refreshed-ID-token verifier applies [OIDC Core 12.2](https://openid.net/specs/openid-connect-core-1_0.html#RefreshTokenResponse): it checks the issuer, subject and audience against the trusted previous verified identity, allows an absent nonce, and requires a present nonce to match the initial digest. It rejects missing, malformed or at-least-five-minute-old ID tokens, requires a strictly later issuance time than the preceding token, and preserves mandatory initial-login nonce verification. The future session deadline must be no later than five minutes after verification, five minutes after issuance or token expiry, whichever is earliest. Its synthetic fixtures do not refresh at the provider, persist tokens or enforce that deadline. Actual Cognito behavior remains unverified.
- A standalone refresh-token protector uses AES-256-GCM with a separate deployment key and authenticates the provider/callback, identity, session and refresh generation. It rejects attempt-key reuse, invalid tokens, tampering and substitution. Key or provider/callback changes invalidate protected tokens. This primitive does not provide persistence, rollback protection, rotation, audit or sessions.
- The Cognito session foundation durably reserves each verified exchange once, then atomically creates or finds an enabled `(issuer, sub)` identity, stores an opaque audited session and an encrypted refresh token, and creates no direct grants or email links. Explicit session source prevents a Cognito session from falling back to local authentication. A local-only manager refuses Cognito sessions; an enabled manager requires a verified provider and matching protector, and authenticates encrypted credential binding on use. Each use rechecks revocation, identity state, idle/absolute expiry and verified-claim freshness. CSRF-checked local logout can revoke an unavailable or expired Cognito session while its cookie is present; logout and local-administrator revocation remove retained provider-token material atomically. An undeployed cleanup worker removes inactive credentials as described below; deployed storage and backup retention remain unverified. No provider refresh, browser login, group-role binding or secured deployment is exposed yet; stale Cognito sessions fail closed.
- The refresh-reservation foundation durably records at most one audited attempt per session and credential generation after rechecking the enabled identity, idle/absolute expiry and provider-bound ciphertext. Stale claims can reserve a refresh but cannot grant access. An unresolved reservation blocks session use and replay, including across restart, while local sessions and CSRF-checked logout remain independent. Reservation audit events are replay-prevention state and must not be deleted while their credential generation exists.
- The standalone provider-refresh exchange sends one verified-HTTPS request after reservation with explicit public-client or Basic authentication and no redirects or automatic retry. It verifies a fresh ID token against the retained identity and original nonce, rejects malformed or present-but-invalid refresh tokens, and encrypts the retained or rotated token for the next generation. The private provider-bound completion proof expires at the earliest applicable claim or session deadline. Synthetic tests cover both client modes, expiration, failures, audit, replay, concurrency and unaffected local login. Failures are audited without tokens where possible; interrupted or failed audit operations may leave only the durable attempt. Errors after operation-ID allocation return that ID without a proof for investigation. The session remains blocked until separate atomic completion. Live Cognito remains unverified.
- The standalone refresh-completion action consumes the private proof once and rechecks its reservation and outcome, unchanged protected credential and verified snapshot, provider/key binding, enabled identity, revocation, source, generation and claim/session deadlines. It atomically updates the verified claims and encrypted retained or rotated token, advances the generation and records redacted success audit. Synthetic tests cover repeated generations, restart, exact deadlines, changed state, concurrency, revocation, audit/commit failure and unaffected local sessions. A failed or uncertain completion must not replay the proof or provider request; losing an uncompleted proof on restart requires a new sign-in.
- An opt-in refreshing session manager requires the same store as its exchanger and can separately resolve a bound session using a trusted browser-marker digest. It coalesces only matching session-token and marker digests, shares a 32-refresh admission limit across bound and unbound work, and bounds each shared operation to 15 seconds. Caller cancellation does not cancel that work; every successful waiter revalidates its session and bound waiters recheck the current marker mapping. Durable reservations prevent another provider request across managers or restarts. Only an exact invalid-session sentinel confirms that the supplied token and binding are invalid; it does not prove that the browser has no competing session or permit replacement. Pending, wrapped, operational and uncertain results must not clear cookies or permit replacement. The authentication-only preview offers explicit CSRF-checked sign-out from its unavailable state without automatic retry. No route supplies a trusted marker, the Console process does not yet enable this manager, and Cognito browser login, group-binding administration and secured deployment remain unfinished.
- The Console process runs separate Cognito-credential and browser-binding cleanup batches at startup and every minute. Each transaction handles at most 100 inactive sessions, with a redacted audit per session; the browser batch rechecks the binding, revokes the old session, removes any retained credential and deletes the current mapping atomically while preserving active mappings and historical session digests. Stale claims or unresolved refreshes alone do not qualify; refresh-reservation audit events remain intact. Each batch has a 10-second deadline. Errors, uncertain outcomes and full batches are logged, local login remains available, larger backlogs require additional ticks, and no cleanup runs while the process is stopped. Corrupt candidates abort the batch and may block later candidates until investigated. The batch limit is not a hard bound on backlog, historical sessions or audit rows. Cleanup prevents revival after a disabled session is processed; the future identity-disable path must revoke sessions atomically. Database/WAL/backup retention and deployed-volume behavior remain unverified.
- The standalone session-grant resolver combines direct roles with an initially empty server-owned mapping of exact issuer and case-sensitive verified groups to global or per-cluster roles. It returns at most the strongest global and requested-cluster grants without group names, and rechecks session/account state, provider/key binding, pending refresh, claim/session deadlines and current mappings in one transaction. Local sessions use direct roles only and do not query the group-mapping table; malformed or unavailable required state fails closed. The separate bound manager action uses a trusted marker digest, refreshes the same bound session if needed, and rechecks current binding, password restrictions and grants before returning a snapshot. Consumers must resolve current grants for each authorization decision; the snapshot is not a delegation. Audited mapping administration, independent Gateway enforcement and deployment remain P54/P55/P59.
- Verify the discovery issuer, configured user pool/client, allowed signing algorithm, JWKS signature/key rotation, expiry and nonce. For ID tokens validate `aud` and `token_use=id`; for any access token validate the intended client (`client_id` and any required audience/scopes) and `token_use=access`. Do not substitute ID/access tokens interchangeably or accept a decoded but unverified JWT.
- Identity key is verified `(issuer, sub)`, not email. Link local/SSO identities only through an authorized explicit flow; do not auto-merge email addresses. Map only configured `cognito:groups` values to application roles; never interpret an arbitrary role header or a matching email domain as ADMIN.
- Use opaque server-side app sessions with rotated CSPRNG identifiers and Secure, HttpOnly, SameSite cookies; store session/temporary recovery identifiers as digests, enforce idle/absolute expiry and CSRF/Origin protection for mutations including security-management endpoints. Encrypt retained provider refresh tokens at rest with a deployment-managed key outside the database; never include callback authorization codes/query strings in request logs. HTTPS is required in secured mode; do not weaken cookies to preserve the existing HTTP-only manual proxy.
- An isolated UI session client implements fixed same-origin HTTPS session requests, relying on the browser to verify TLS. It includes same-origin cookies, forbids redirects and caching, bounds request time, validates session responses and supplies the host-only CSRF cookie on password changes and logout. Missing CSRF fails before dispatch; network or malformed mutation responses have an unknown outcome and are not automatically retried. Session expiry, bad credentials, throttling and service errors are distinct.
- Building with `VITE_KAFKA3O_CONSOLE_AUTH_PREVIEW=true` selects an authentication-only local sign-in, temporary-password-change and logout preview. It never mounts the legacy Gateway shell or sends Kafka requests, even if the manual-proxy flag is also set. The normal build remains unchanged. The preview requires a verified HTTPS origin with the Console API on that same origin; the current manual HTTP deployment does not provide it. Unknown password-change outcomes are kept in memory during the page lifetime and require explicit audit acknowledgement before retrying; reload loses that UI reminder, so the audit remains authoritative. An opt-in cross-repository fixture executes the built bundle against the real loopback Console API using a separate synthetic SQLite store and a test CA trusted only by the Node HTTPS client. It verifies the chain, hostname, login, password replacement and logout. A separate administrator client revokes the preview session; after its next request receives 401, the preview discards signed-in state without replay or legacy Gateway requests. jsdom simulates the DOM and cookies. Native-browser TLS and cookie validation and an HTTPS deployment are not yet verified. The preview is not deployed and does not provide SSO, Gateway authorization or Kafka access.
- The local-session foundation stores session and CSRF token digests and defaults to 30 minutes idle/eight hours absolute (configurable, with a 24-hour maximum). Password replacement increments the credential version and revokes existing local sessions atomically with audit. Local-account state and administrator-reset services recheck the current local global ADMIN session and grants transactionally; state changes protect the last enabled local global ADMIN, and both operations revoke target sessions. The loopback HTTPS state route requires an explicit boolean, derives its actor from the session, checks exact Origin and session-bound CSRF, rejects duplicate or untrusted fields, and reports a correlated outcome. A successful self-disable clears its browser cookies; audit failure blocks the mutation. Reset reserves a durable 15-minute quota of 10 per existing target, 60 per authorized administrator and 300 globally, counts invalid passwords and targets, rechecks authorization after hashing, requires another password change, and uses a credential-version compare-and-swap. It rejects replay and stale reservations; audit failure blocks the change. The loopback HTTPS reset route derives its actor from the authenticated session and requires the exact Origin and session-bound CSRF header. Unknown commit or lost-response outcomes must be investigated, using the operation ID when available, not automatically retried. A loopback-only `cmd/console serve` process mounts the session, listing, creation, reset and state handlers; it requires direct TLS 1.2+, an exact HTTPS origin, a matching currently valid server certificate, and a bootstrapped enabled local global ADMIN. Clients must verify the certificate chain and hostname. The process exposes no Kafka or grant-management routes and is not deployed; native-browser integration, Kafka-route protection, administrator recovery and the complete session boundary remain unwired.
- Session/role revocation is checked on each authorization decision. Refresh verified Cognito group claims at most every five minutes (or earlier token expiry); block access if revalidation is required and fails. External Cognito group/removal/sign-out propagation must be verified with the actual pool and documented honestly; local disable/session revocation provides immediate application-side denial on the next request.
- Session administration remains limited to a current local global ADMIN without a pending password change. The loopback HTTPS API lists non-revoked local and Cognito sessions within idle/absolute lifetimes in bounded, non-snapshot pages and revokes an individual session using its opaque, noncredential session ID; both services transactionally recheck the actor's session and grant. Cognito entries identify their source and may be listed when claims are stale, but stale sessions cannot be used. The no-store listing excludes credentials and their digests, and an audit or commit failure returns no data. Revocation requires exact Origin and session-bound CSRF, and the mutation and its redacted successful audit commit atomically; audit failure blocks it and an unknown outcome is not automatically retried. Confirmed or uncertain self-revocation clears the browser cookies without disabling the account or its other sessions. The authentication-only preview's revoked-session handling is verified in a simulated DOM with real HTTPS; secured Kafka enforcement and user-scoped cache clearing remain P55/P59, not claims about the existing preview.
- Logout invalidates the local session first, clears user-scoped query caches and initiates configured Cognito logout when appropriate. Do not promise logout from every upstream federated provider. After login/recovery, refresh permissions/state; never replay an interrupted mutation.

### Authorization model and Production policy
- Initial grant roles are `VIEWER < OPERATOR < ADMIN`. Resolve the highest applicable global or per-cluster role; global grants apply to all registered clusters and per-cluster grants add access only there. No grant means deny. There are no explicit deny rules or cluster overrides that subtract global access in M10; show effective access and grant sources in the management UI.
- Global ADMIN includes Console account/session/group-binding/policy management and global audit access. A per-cluster ADMIN grants that cluster's data operations and scoped operational audit only; it cannot change global grants, the trusted Gateway registry or the Production classification. Keep these management permissions distinct in the action catalog even when global ADMIN grants them initially.
- Store explicit Production/non-Production classification centrally; unclassified or unknown environments deny Kafka mutations. Classification changes require global administrative permission, confirmation, reason and audit. New decisions after the change use the new classification; already-authorized in-flight Kafka requests are not retrospectively canceled.

| Action | VIEWER | OPERATOR | ADMIN |
| --- | --- | --- | --- |
| Permitted cluster metadata, messages, consumer groups, config/status reads | Allow | Allow | Allow |
| Supported Kafka mutations, explicitly non-Production cluster | Deny | Allow | Allow |
| Supported Kafka mutations, Production cluster | Deny | Deny | Allow, with confirmation and change reason |
| Mutations, missing/unknown environment | Deny | Deny | Deny until explicitly classified |
| Console identity/role/cluster-policy management | Deny | Deny | Global ADMIN only |
| Audit read/export | Deny | Deny | Scoped to cluster grant, or all scopes for global ADMIN |

- Maintain an explicit server action catalog, not a generic HTTP-method-only policy. Current write actions are `messages.produce`, `topics.create`, `topics.delete`, `topics.config.alter`, `brokers.config.alter`, `topics.partitions.increase` and `topics.replicas.reassign`. Map every read endpoint too; future routes default to deny until classified. Kafka read-only/sensitive metadata and existing validation are additional restrictions, never overridden by ADMIN.
- Production is an additional condition on Kafka mutations **only when the cluster is Production**. Non-Production does not require ADMIN, but it does require the normal OPERATOR/ADMIN grant. Identity/policy mutations are independently administrative in every environment.

### Browser → Console → Gateway trust flow
1. The browser sends the opaque Console session cookie to same-origin APIs. The backend checks session, CSRF, target registration and requested action; it strips client-supplied identity/role/delegation headers and never accepts arbitrary forwarding URLs.
2. The Console creates a CSPRNG opaque delegation handle, short-lived (at most 30 seconds), single-use and bound to the active user session, configured Gateway/cluster ID, normalized action/resource, method, request-body digest, and Production reason if applicable. Store only its digest; never put the handle in a URL, browser response or log.
3. The Console forwards to the configured Gateway over verified TLS using deployment-managed service authentication **and** the delegation. A service credential alone is not user authorization. No automatic proxy/HTTP retry is permitted for a mutation.
4. The Gateway derives action/resource from its own actual route and validated request, and asks the Console policy API to validate/consume the delegation over an authenticated, verified-TLS channel. The policy API checks the Gateway's own identity/target binding, current user/session/grants/classification, request binding and expiry; delegation consumption, authorization decision and required durable mutation-intent insertion are atomic. Return only the actor/decision context the Gateway needs.
5. Only an allow decision for that exact request permits the Gateway's Kafka action. Reject missing/invalid identity with 401, valid-but-forbidden with 403, and unavailable policy/audit with a distinct 503 problem code. Unknown actions, replayed handles, wrong-cluster requests and spoofed headers never reach Kafka. Every protected request gets a current policy decision; stale signed/browser capability snapshots cannot bypass a newly set Production flag or revocation.
6. The Gateway appends the correlated operation outcome through its authenticated audit interface and returns the existing result/error shape. Acceptance remains distinct from completion; timeouts remain potentially accepted. Policy or auditing failures never trigger fallback to legacy authentication or re-execution.

This design deliberately uses the existing central store for opaque delegation/introspection rather than introducing a second JWT issuer or distributing local passwords to Gateways. The [gateway-service-trust discovery](./discovery/gateway-service-trust.md) fixes the contract: a dedicated service CA issues TLS 1.3 mTLS certificates with exactly one URI SAN (`spiffe://kafka3o/console`, `spiffe://kafka3o/gateway/<clusterID>`), checked on every hop; the handle travels only in `X-Kafka3O-Delegation` (32 random bytes, base64url) and is stored as SHA-256; binding v1 is `SHA-256("kafka3o-delegation-v1\n" + clusterID + "\n" + METHOD + "\n" + escapedPath + "\n" + sorted query + "\n" + hex(SHA-256(exact body)))`, with duplicate query keys rejected and exact bytes forwarded; the policy API is a separate Console mTLS listener (`POST /internal/v1/delegations/consume`); the budget is 1 s policy + 3 s Kafka + 1 s outcome audit per Gateway request, 6 s Console→Gateway and 8 s browser→Console. Service-certificate issuance and rotation on EKS-D is decided in P59. Authenticate both Console→Gateway and Gateway→policy/audit service calls with scoped credentials; do not reuse a browser session or Cognito token as the Gateway's service credential. A policy-service outage denies protected operations; anonymous process liveness must remain usable.

### Durable audit and operational behavior
- Use correlated append-only intent/decision/outcome events with server UTC time, event/operation/request IDs, stable actor ID, local/Cognito auth source, effective grant/policy revision, registered cluster/environment, action/resource, permit/deny reason and sanitized outcome. Record security administration, login failures, denials, mutations, audit reads and exports; normal successful metadata polling is not an audit event in M10.
- Write authorization/intent durably before any Kafka mutation. Append validation rejection, failed-before-send, accepted, confirmed or unknown outcomes as appropriate; retain an unresolved intent after crash or lost response. An audit timeline must not claim a reassignment completed just because Kafka accepted it.
- If intent persistence fails, no Kafka mutation starts. If an outcome cannot be persisted after possible Kafka acceptance, return explicit uncertainty with a correlation ID and emit an operational alert; the durable intent remains unresolved. Recovery inspects actual state and never automatically replays writes.
- Do not log passwords, cookies, Authorization/delegation/provider tokens, raw request bodies, message keys/payloads/headers or sensitive config values. Audit configuration changes by setting name/operation with value redaction; record partition counts/replica IDs only as safe metadata. Sanitize user-supplied reasons to prevent log injection.
- Enforce global/cluster audit scope server-side, including pagination and export. Application roles have no audit-edit/delete API; restrict access to the SQLite file to the Console process and separately authorize application audit reads/writes. SQLite has no database-user privilege separation; a process or administrator with file access can alter the database, so append-only application behavior is not tamper-proof storage. Controlled retention, SQLite-consistent backups and recovery protect account/policy/audit continuity.

### Gateway HTTP API v1 (consumed by the UI)
- Base URL: per gateway, from the UI's `/config.json`; M5 requires HTTPS and an `Authorization: Bearer` token for all requests except anonymous liveness and allowed-origin CORS preflight
- `GET /api/v1/health/live` → 200 while the process is up
- `GET /api/v1/cluster` → `{clusterId, controllerId, brokers:[{id, host, port, rack}]}`; 503 `cluster_unreachable` when Kafka is unreachable
- `GET /api/v1/topics` → `[{name, partitions, replicationFactor, internal, approxMessages}]`; 503 `cluster_unreachable`
- `GET /api/v1/topics/{topic}` → `{name, partitions:[{id, leader, replicas, isr, startOffset, endOffset}], config:[{name, value, sensitive}]}`; sensitive config values are not sent, 404 `not_found` when the topic is absent, 503 `cluster_unreachable` for Kafka failures
- `GET /api/v1/topics/{topic}/messages` → at most 50 `{partition, offset, offsetExact, timestamp, key, value, headers:[{key, value}]}` records across the topic, newest first by default; `offsetExact` is the decimal string for the existing numeric `offset`, preserving int64 precision in browsers, and Kafka byte fields are base64 strings or `null` for Kafka nulls. Optional `partition` plus exactly one of `offset` or `timestamp` reads from that position in offset order (`timestamp` is Unix milliseconds); invalid positions return 400 `invalid_position`, a missing topic returns 404 `not_found`, and Kafka failures return 503 `cluster_unreachable`
- `GET /api/v1/topics/{topic}/messages/search?query=<text>` → `{messages, scanned, truncated}`; searches case-sensitive UTF-8 query bytes in keys and values over at most 500 recent offset positions across the topic. `scanned` is the number of records examined, and `truncated` indicates positions or partitions outside the bounded window. Offset order and timestamps are not globally correlated; the window is not a claim of the newest 500 by timestamp. Empty or invalid UTF-8 search returns 400 `invalid_search`; missing topics return 404 `not_found` and Kafka failures 503 `cluster_unreachable`.
- `POST /api/v1/topics/{topic}/messages` accepts `{value: string, key?: string, headers?: [{key: string, value: string}]}` as UTF-8 JSON. Empty values and keys are allowed; omitted key differs from an empty key. Acknowledged delivery returns `{partition: number, offset: string}` with an exact decimal offset. Invalid requests are rejected; 503 `delivery_unknown` means the message may already have been written and must not be automatically retried. The dedicated producer does not automatically retry records.
- `GET /api/v1/consumer-groups` → consumer groups with `id`, `protocol`, `state`, `members`, `topics`, and per-topic/partition offsets and lag. Offsets and lag are decimal strings or `null` to preserve int64 precision. Partition status is `ok`, `no_commit`, `out_of_range`, or `unavailable`; an unavailable partition or group includes an explicit error. Topic membership is based on explicit subscription, current assignment, or committed offset. List/describe classic and next-generation consumer groups using Kafka 3.8+ group-type filtering.
- `POST /api/v1/topics` accepts `{name: string, partitions: number, replicationFactor: number}` and returns 201 with those fields on broker acknowledgement. Topic names use 1–249 ASCII letters, digits, `.`, `_` or `-` and cannot be `.` or `..`; counts must be positive int32 and int16 respectively. Invalid input returns 400/422, duplicates return 409 `topic_exists`, and 503 `topic_write_unknown` means creation may already have succeeded. Administrative writes are not automatically retried.
- `DELETE /api/v1/topics/{topic}` returns 202 `{name, status: "accepted"}` when the broker accepts deletion; completion can be asynchronous. Invalid names return 400, missing topics 404 `not_found`, and 503 `topic_write_unknown` means deletion may already have succeeded. Neither gateway nor UI automatically retries.
- `GET /api/v1/topics/{topic}/config` and `GET /api/v1/brokers/{brokerId}/config` return `[{name, value, sensitive, readOnly, source, type, documentation?}]`. Sensitive/password values and documentation are suppressed. Broker settings are per broker, not the cluster-wide default resource; restart-required settings remain read-only.
- `POST` to either configuration path accepts `{name, operation: "set" | "reset", value: string | null}` and returns `{name, status: "accepted"}`. Kafka validates before one incremental apply; reset removes only that resource's override. Invalid/missing/read-only/denied/rejected requests have explicit problem codes; 503 `configuration_write_unknown` means it may have applied. No automatic write retry.
- `POST /api/v1/topics/{topic}/partitions` accepts `{count}` as a larger absolute partition count and returns 202 `{topic, status: "accepted"}` after Kafka validation and one apply. An increase is irreversible; 503 `partition_write_unknown` requires verification before retrying.
- `GET /api/v1/topics/{topic}/reassignments` returns active `[{partition, replicas, addingReplicas, removingReplicas}]`; `POST /api/v1/topics/{topic}/partitions/{partitionId}/replicas` accepts `{replicas: [brokerId, ...]}` and returns 202 `{topic, status: "accepted"}`. Broker IDs must exist and be distinct/nonempty; active reassignments are rejected, and empty/nil lists never cancel them. Requests are not retried; accepted placement can continue asynchronously and 503 `partition_write_unknown` requires verification.
